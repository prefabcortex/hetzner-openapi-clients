# hetzner-api

Strictly typed Python client (sync + async) for the **Hetzner API**, generated by
`openapi-python-generator`. Do not edit by hand - regenerate instead.

- Python >= 3.14, `httpx2` + `pydantic` v2, ships `py.typed`
- `ruff` (all rules), `mypy --strict` and `pyright` (strict) clean, 100 % test coverage
- Sync (`Hetzner`) and async (`AsyncHetzner`) clients with identical APIs
- Automatic retries, typed exceptions

## Usage

More in [`examples/`](examples): configuring the client, async, lax/strict
validation, and one function per operation with example values from the spec
(`examples/operations/`).

```python
from hetzner_api import Hetzner

with Hetzner() as client:  # token from $HCLOUD_TOKEN or Hetzner(token="...")
    server = client.servers.get_server(1)
```

Every response is a frozen, validated pydantic model. Nested request objects are `TypedDict`s
(`...Param` in `hetzner_api.params`), so plain dicts are type-checked too. Optional body
arguments default to `NOT_GIVEN` and are left out; `None` is sent as JSON `null`.

Names come from the spec: each tag is an attribute of the client (`Order Items` →
`client.order_items`), each `operationId` a method in snake_case (`cancelOrder` →
`cancel_order`). Path parameters are positional arguments, everything else is a keyword
argument. Responses are the models of the spec as they are.

### Authentication

The client takes these credentials (keyword arguments):

- `token`: API token, sent as `Authorization: Bearer`. Default: `$HCLOUD_TOKEN`.

Each operation sends the credentials its spec asks for; an operation whose
credentials are missing raises `HetznerError` before anything is sent. Credentials
never appear in `repr()`, logs or pickled errors. More in `examples/auth.py`.

Enum arguments are `Literal` types. A list kept in a variable needs the enum type as annotation
(from `hetzner_api.models`), otherwise it is inferred as `list[str]`.

### Errors

```python
from hetzner_api import HetznerError, NotFoundError

try:
    client.servers.get_server(1)
except NotFoundError as error:
    print(error.status_code, error.error)  # the error schema of the spec, parsed
except HetznerError:
    ...  # base class of everything the client raises
```

`APIStatusError` has one subclass per status (400, 401, 403, 404, 409/423, 412, 422, 429, 5xx).
`error` is the body as the schema the spec names for that operation and status (`None` if it
names none or the body does not match), `body` the raw JSON, `retry_after` the seconds of a
`Retry-After` header and `problem` an RFC 9457 `application/problem+json` body
(`ProblemDetails`), whatever the spec says.
Network problems raise `APIConnectionError`/`APITimeoutError`. With `validation="strict"`, a
response that does not match the spec raises `ResponseValidationError` - the request itself has
already been executed (see below).

### Retries, timeouts, logging

```python
from hetzner_api import RetryPolicy

client = Hetzner(timeout=10.0, retry=RetryPolicy(max_retries=3, max_delay=30.0))
# timeout=None disables the timeout; without the argument it is 30 s (or that of http_client)
```

Retried automatically:
- `429` responses;
- connection failures where the request was never sent;
- for idempotent methods only (not `POST`/`PATCH`): `502`/`503`/`504` and network errors during
  the exchange (read/write timeouts, dropped connections).

`Retry-After` is honoured.

The client logs to the `hetzner_api` logger: each request on `DEBUG`, retries on `INFO`.

### Async

```python
from hetzner_api import AsyncHetzner

async with AsyncHetzner() as client:
    server = await client.servers.get_server(1)
```

### Validation: lax or strict

Specs do not always describe their API exactly. By default (`validation="lax"`) the client
gets along with what the API sends: rules of the spec (`maxLength`, `pattern` …) are not
checked, and a response that does not match the spec is still returned - everything that fits
is validated, the rest is kept as sent and a warning is logged.

For checking an API against its spec, hold it to every rule:

```python
from hetzner_api import RequestValidationError, ResponseValidationError

client = Hetzner(validation="strict")
# arguments breaking a rule raise RequestValidationError before anything is sent,
# responses breaking a rule or the schema raise ResponseValidationError
```

### Unknown enum values

New values the API introduces later do not break parsing; they arrive as `UnknownValue`
(a `str`), which is visible in the types:

```python
from hetzner_api import UnknownValue

match value:
    case "known_value":
        ...
    case UnknownValue():
        ...
```

## Versioning

This package has its own SemVer line. The API version (`1.0.0`) is
*provenance*, not the package version - it is recorded in `.prefabcortex-generation.json` together with the
checksum of the specification and the version of the generator. A specification may go from
2.1.13 to 2.1.14 and rename a field, while another jumps a minor without changing a single
signature: the version of the API says nothing about the code.

How far a release counts is measured, not chosen: `uv run poe check:api` (`griffe`) compares
the public API with the last tag.

| The check reports | Release |
| --- | --- |
| a break in the public API | **major** - `2.4.1` becomes `3.0.0` |
| no break | **minor** - `2.4.1` becomes `2.5.0` |

There are no patch releases: the check finds breaks, not additions, so anything that changed
without breaking is released as a minor - and a constraint such as `~=2.4` never installs a
break.

Modules starting with an underscore (`_base_client`, `_auth`, `_validation` …) are the package's
plumbing and may change in any release. Everything else is the contract: the clients, resources,
models, `params`, errors and helpers such as `rules`.
